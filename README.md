# ABOUT

Учебный проект по курсу "Highload Architect (Otus)"
Текущее состояние - вплодь до ДЗ 5 (Шардирование)

## Локальный запуск

### 1. Citus и Redis

Требуется Docker. Основной запуск из корня репозитория:

```bash
make up
```

Команда поднимает Citus coordinator на `localhost:5435`, два worker-узла и Redis,
дожидается регистрации worker-узлов, применяет миграции и запускает HTTP-сервер.
Используется закреплённый образ `citusdata/citus:14.2.0`, проверенный на
PostgreSQL 18.4. Остановить кластер: `make down`; проверить worker-узлы:
`make status`.

Параметры по умолчанию (см. [database/Makefile](database/Makefile)):

| Параметр | Значение |
|----------|----------|
| Host | `localhost` |
| Port | `5435` |
| User | `someuser` |
| Password | `somepass` |
| Database | `socialnet` |

Подключение к coordinator вручную (psql): `make connect`

**Миграции:** при первом создании БД выполняется `database/migrations/init/init.sql`. После запуска одиночной БД или кластера примените все пронумерованные миграции из корня репозитория (требуется `psql`):

```bash
make migrate
```

Команда применяет файлы по порядку к coordinator на порту 5435 и останавливается при ошибке. Каждая миграция выполняется в отдельной транзакции. Существующие миграции допускают повторный запуск; новые также должны быть повторно применимыми. `make up` запускает миграции автоматически после готовности Citus worker-узлов. `init.sql` выполняется только при создании пустого хранилища PostgreSQL, а не при каждом запуске контейнера.

### 2. Backend

```bash
cd backend
go run ./cmd/app
```

Сервер по умолчанию слушает на порту `:3000` (переменная `HTTP_ADDR`).
URL coordinator задаётся переменной `DATABASE_URL_MASTER`. Лента друзей требует
Redis; его URL задаётся переменной `REDIS_URL`.

Эндпойнты изменения друзей и постов требуют заголовок `Authorization: Bearer <token>` с токеном из `/login`. Чтение поста открыто для всех. Изменять и удалять пост может только автор; чужой или отсутствующий пост возвращает `404`.

### Диалоги и шардирование

`dialog_messages` — hash-distributed таблица Citus по `dialog_id`. Этот ключ детерминированно рассчитывается как UUIDv5 от отсортированной пары участников, поэтому оба направления одного диалога всегда попадают на один shard. Миграция создаёт 32 shard'а, поровну распределённых между двумя worker-узлами. Шардирование по паре пользователей сглаживает «эффект Леди Гаги»: многочисленные личные диалоги популярного пользователя хешируются независимо.
Единственный чрезвычайно активный диалог остаётся на одном shard'е и может сильно нагрузить его — это осознанный компромисс ради локального упорядоченного чтения истории.
`GET /dialog/{user_id}/list` использует cursor-pagination по `(created_at, id)`:

```text
GET /dialog/{user_id}/list?limit=50&cursor=<next_cursor>
```

Ответ имеет форму `{"items":[...],"next_cursor":"..."}`. `next_cursor` отсутствует на последней странице. Допустимый `limit` — от 1 до 100, по умолчанию 50. Для этого поменяли контракт в `openapi.json`.

Чтобы добавить worker без даунтайма, нужно зарегистрировать его через
`citus_add_node`, проверить план `get_rebalance_table_shards_plan`, затем
запустить `citus_rebalance_start()`. В Citus 14 чтения и записи могут продолжаться
во время переноса существующих shard'ов. Изменение количества shard'ов — отдельная
операция `alter_distributed_table`; перед ней следует проверить поведение и окно
обслуживания на версии и нагрузке целевого окружения.

Тесты backend выполняются командой `cd backend && go test ./...`. 

Тест использует временную таблицу в отдельной сессии и не меняет данные приложения.

### 3. Тестовые посты и ленты

После импорта или регистрации пользователей можно создать воспроизводимый
тестовый социальный граф и посты:

```bash
cd backend
go run ./cmd/import-posts \
  -posts 100000 \
  -friends-per-user 10 \
  -days 30 \
  -file /path/to/posts.txt \
  -reset
```

`-file` необязателен: без него импортёр создаёт простые тексты сам. Файл должен
содержать по одному тексту поста на строку; для задания можно использовать
предложенный `posts.txt`. Флаг `-reset` явно очищает только `posts`,
`friendships` и очередь перестроения перед загрузкой. Без него существующие
данные остаются, а новые связи добавляются без дубликатов. Напечатанный в конце
`seed` можно передать через `-seed`, чтобы повторить распределение авторов и
времени публикаций.

Импортёр создаёт для каждого пользователя направленные связи с ближайшими
`friends-per-user` пользователями, добавляет посты через PostgreSQL `COPY` и
после коммита ставит ленты в очередь перестроения. Redis обновится фоновым
воркером или при первом обращении к соответствующей ленте.

### 4. Проверка API

**curl:**

```bash
# регистрация
curl -s -X POST http://localhost:3000/user/register \
  -H 'Content-Type: application/json' \
  -d '{"first_name":"Иван","second_name":"Иванов","birthdate":"1990-01-15","biography":"Всегда","city":"Москва","password":"secret"}'

# анкета
curl -s http://localhost:3000/user/get/<user_id>

# поиск анкет
curl -s 'http://localhost:3000/user/search?first_name=Ива&last_name=Ива'

# логин
curl -s -X POST http://localhost:3000/login \
  -H 'Content-Type: application/json' \
  -d '{"id":"<user_id>","password":"secret"}'
```

**Postman:** импортируйте коллекцию [postman/highload_hw.json](postman/highload_hw.json). Запустите запросы по порядку: Register → Get user → Search users → Login. Переменные `userId` и `token` заполняются автоматически из ответов. Для проверки диалога зарегистрируйте второго пользователя и укажите его ID в `dialogUserId`; `dialogCursor` сохраняется автоматически после первой страницы.

## API

| Метод | Путь | Описание |
|-------|------|----------|
| POST | `/user/register` | Регистрация пользователя |
| GET | `/user/get/{id}` | Получение анкеты |
| GET | `/user/search` | Поиск анкет по префиксам имени и фамилии (`first_name`, `last_name`) |
| POST | `/login` | Аутентификация, выдача токена |
| PUT | `/friend/set/{user_id}` | Добавление друга (нужен токен) |
| PUT | `/friend/delete/{user_id}` | Удаление друга (нужен токен) |
| POST | `/post/create` | Создание поста с JSON `{"text":"..."}` (нужен токен) |
| PUT | `/post/update` | Изменение своего поста с JSON `{"id":"...","text":"..."}` (нужен токен) |
| PUT | `/post/delete/{id}` | Удаление своего поста (нужен токен) |
| GET | `/post/get/{id}` | Получение поста |
| GET | `/post/feed?offset=0&limit=10` | Лента последних постов друзей из Redis (нужен токен) |
| POST | `/dialog/{user_id}/send` | Отправка сообщения пользователю (нужен токен) |
| GET | `/dialog/{user_id}/list?limit=50&cursor=...` | Страница диалога с пользователем (нужен токен) |

Лента хранится в Redis для каждого пользователя и содержит не более
1000 последних постов его текущих друзей. Изменения дружбы и постов в той же
транзакции добавляют задачу в PostgreSQL; фоновый воркер перестраивает кеш, а
первое чтение конкретной ленты синхронизирует её сразу, это также
позволяет восстановить кеш после перезапуска Redis без потери инвалидаций.
